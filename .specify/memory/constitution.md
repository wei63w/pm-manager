

# PM Manager 宪章



## Core Principles



### I. 本地优先的持久资产（不可协商）

治理数据必须存放在独立元数据目录（目标项目中的 `.pm/`）。该目录必须保存 AI
导航地图、文档索引、评审记录、开发日志与编码规范库。禁止污染业务源代码。
`.pm/` 必须通过 `.git/info/exclude` 排除，禁止写入共享的 `.gitignore`。

资产必须在会话关闭与重启后仍然可用。新会话必须加载已有治理数据；元数据有效时
禁止强制全量重扫。扫描、文档生成、评审、体检与迭代对话必须留下审计记录（操作人、
时间、输入、输出；若该步由 AI 产出，还须包含推理过程）。必须支持按时间范围导出
审计日志。元数据损坏或检测到项目文件变更时，必须触发修复或增量更新，禁止静默丢
失，也禁止无条件全量重扫。

**理由**：会话丢失、历史不可复用、过程不可审计，是本产品要关掉的根因（PRD §5.1）。

### II. 先确认后写入（不可协商）

Agent 必须先给出方案，等待用户明确确认后，才可写入应用代码、SQL、云资源，或将
生成的文档与规范落盘。默认行为必须是只报告、不侵入。未经确认的 PRD 或宪章禁止
当作项目基线。

文档补齐必须提供两种模式：用户上传/手写，或由 AI 根据代码、注释与 git 历史起草
—— AI 草稿必须可编辑，且必须在用户确认后才落盘。用户确认过的问题与规则，随后可
以约束代码生成、评审与体检。

**理由**：自动写入会把幻觉输出写进仓库。人确认是治理不变成篡改的控制点
（PRD §6.2、§6.3、§7.3）。

### III. 地图优先协作

Agent 必须先读项目导航地图与文档索引，再决定是否遍历目录。地图或索引已存在时，
为「找东西」而做无过滤全库递归遍历视为缺陷。扫描必须忽略 `node_modules`、构建
产物、日志以及配置的忽略清单。必须同时提供全量扫描与增量扫描；增量扫描必须只分
析变更文件。

文件变更后，应当在后台静默增量更新元数据与地图。单个文件解析失败禁止中断整批流
程。产品必须能在元数据区生成 Mermaid 架构图、依赖图、流程图以及带注解的目录树
（若用户要求这些产物落到业务代码树，仍须走确认门）。

**理由**：盲目遍历是一等 Token 成本。地图是人与 Agent 之间便宜、可复用的契约
（PRD §3.2、§5.2.2）。

### IV. 有证据的质量闭环

评审或质量结论必须包含推理链与对应代码片段。空泛、纯文风、无证据的结论必须判定
为不合格。用户必须能将发现标记为确认问题、误报忽略或待优化。已确认的真实问题与
高频踩坑必须沉淀进团队规范库，并在后续生成、评审、体检中加载。

P0（阻断 / 高危）必须打断。P1 与 P2 必须汇总进报告，禁止劫持日常循环。V1.0 必须
交付带推理链的增量 Diff 评审。周期性全量体检、Git 钩子强制、单测辅助、高危标记
属于 V1.1：除非某份规格明确纳入，否则禁止阻塞 V1.0 交付。

**理由**：又快又像又错，是幻觉模式。闭环是发现 → 确认 → 沉淀规则 → 下次拦截  
（PRD §5.3、§5.5.5、§6.4、§8）。

## 附加约束

以下为产品 PRD 中的非功能门禁。计划若无法满足某条门禁，必须在 Complexity
Tracking 中记录豁免，并写明被否决的更简方案。

**文档中文优先**

- 宪章、规格（spec）、实施计划、任务清单、PRD、以及面向使用者的治理说明，正文
必须使用中文。
- 代码标识符、CLI 子命令、斜杠命令名、仓库路径必须保持现有英文，禁止为「中文化」
而重命名对外接口。
- 面向 GitHub / skills.sh 发行的 `README.md` 默认英文，并链到中文版 `README.zh-CN.md`；
原则变更时，两份 README 的原则摘要必须与中文宪章一致。
- 用户以中文交互时，生成的评审结论、待办、报告必须使用中文。

**性能（中小型项目；除非规格另行声明）**

- 全量扫描必须在 ≤ 30s 内完成。
- 增量扫描必须在 ≤ 5s 内完成。
- 导航地图与资产加载必须达到秒级，禁止成为阻塞等待。
- 单次 Diff 评审必须在 ≤ 15s 内完成。
- 全项目体检（V1.1）必须在 ≤ 2 分钟内完成。

**稳定性**

- 元数据必须在进程异常退出后仍可恢复。
- 扫描、评审、生成必须隔离单文件失败。

**安全性**

- 对话记录与项目摘录在持久化或导出前必须脱敏（密钥、凭证、私钥、明显个人身份
信息）。
- 生成内容未经确认禁止落入业务代码树。

**产品边界**

- 这是开发者侧的本地治理工作台。禁止做成云端项目管理套件，也禁止替代
Jira/Linear。
- Spec Kit 仍负责功能交付（规格 → 计划 → 任务 → 实现）。PM Manager 仍负责健康
与下一步。二者可以共存；任何一方禁止静默覆盖对方产物。

**V1.0 范围冻结**

范围内：元数据持久化与审计、核心文档检测/补齐与一致性校验、结构扫描 + Mermaid

- AI 地图、Diff 评审 + 推理链 + 基础规范沉淀、对话落盘 + 基础意图解析。

推迟到 V1.1：周期性全量体检、单测辅助、高危文件标记、配置模板/规则启停、批量导出

- Git 钩子、幻觉防御升级。



## 研发流程

1. 改变产品行为的功能必须从可追溯到 `docs/prd.md` 或已确认的 `.pm/prd/prd.md` /
  宪章的规格开始。未确认草稿禁止当作验收标准。
2. `/speckit-plan` 的 Constitution Check 必须在 Phase 0 调研前通过，并在 Phase 1
  设计后复检。无正当理由的违规必须阻断。
3. CLI、脚手架、持久化变更必须为新行为提供 pytest 覆盖（成功路径 + 至少一条失败/
  隔离用例）。
4. 编辑 Agent 命令模板（`skills/pm-manager/templates/commands/`）时，必须保持
  「先确认后写入」规则。
5. 优先增量更新元数据，而非全量重扫；优先读地图/索引，而非递归遍历；优先沉淀规则，
  而非永远重复同一发现。
6. 额外依赖、后台守护进程、云调用、常驻监视必须说明必要性。默认是按需扫描，禁止
  默认后台常驻。
7. 本仓库治理文档（宪章、规格、计划、任务、PRD）填写与修订必须中文优先。



## Governance

本宪章高于与之冲突的口头习惯、README 口号与临时 Agent 做法。模板、技能或 CLI
路径与上述原则冲突时，以原则为准，直至本文件被修订。

**修订程序**

1. 写明要改的原则或约束，以及原因。
2. 修改 `.specify/memory/constitution.md` 并提升版本号。
3. 同步计划 / 规格 / 任务模板以及运行时说明（`README.md`、
  `skills/pm-manager/AGENTS.md`）。
4. 在本文件顶部记录 Sync Impact Report。
5. 禁止把「只改了 PRD」当作宪章修订；PRD 变更必须显式提升到本文件。

**版本规则**

- MAJOR：删除或重定义原则，或翻转一条不可协商条款。
- MINOR：新增原则/章节，或实质性扩展指导。
- PATCH：澄清、措辞、错别字、非语义打磨。

**合规审查**

- 每份实施计划必须按 `.specify/templates/plan-template.md` 填写 Constitution
Check。
- 触及 `.pm/` 模板、CLI 脚手架或 `/pm-*` 命令的变更，必须核对原则 I–IV（持久化
位置、先确认后写入、地图优先 I/O、有证据的评审输出、脱敏）以及
文档中文优先。
- 运行时说明：`skills/pm-manager/AGENTS.md` 与 README Core Philosophy。
