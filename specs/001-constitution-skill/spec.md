## User Scenarios & Testing *(mandatory)*

本功能把宪章 v1.1.1 的四条核心原则落实为编码助手里可安装的治理技能。使用者是仓库内的研发人员；他们用少量英文斜杠命令完成治理，中文阅读结果。技能只服务**当前工作区那个仓库**，在旁边建立独立治理台，不替代规格驱动的「做什么」交付链，也不做云端项目管理。

范围以宪章 V1.0 冻结为准。

### User Story 1 - 治理台一次建好、换会话还能用 (Priority: P1)

研发人员在某个仓库第一次启用技能。技能在业务代码旁边建好独立治理台：地图、说明索引、评审、日志、规范、待办都放这里。业务文件默认不被改写。关掉对话再开，只要还在同一仓库，上次的东西还在，不必把整个仓库重新翻一遍。治理台坏了或文件变了，要修复或只更新变化部分，不能悄悄当新项目，也不能一声不吭全量重扫后盖掉用户已确认的内容。

**Why this priority**: 对应宪章原则 I。没有跨会话资产，其余故事没有落点。

**Independent Test**: 未治理仓库执行初始化 → 确认治理台出现且业务树未被写入 → 结束会话再开 → 状态查看能读到上次资产且未做全库重扫。

**Acceptance Scenarios**:

1. **Given** 仓库尚无治理台，**When** 用户启用技能并初始化，**Then** 独立治理台被创建，业务源码默认零写入，治理台被标为仅个人本地、不进入仓库共享忽略规则。
2. **Given** 治理台已存在且内容完好，**When** 用户新开对话后查看状态，**Then** 直接加载已有资产，不强制全量重扫。
3. **Given** 治理台损坏或项目文件已变，**When** 用户再次使用技能，**Then** 提示并修复或按变更增量更新，禁止静默丢数据，禁止无提示全量覆盖已确认内容。
4. **Given** 仓库里几乎没有业务代码，**When** 用户初始化，**Then** 仍能建起治理台；产品说明要么来自用户一句话，要么标明信息不足，禁止虚构模块。

### User Story 2 - 先确认基线，再允许写东西 (Priority: P1)

初始化时技能必须停下来等人拍板。仓库若已有规格驱动宪章或功能规格，技能导入它们，摘要给用户，等确认 / 修订 / 跳过。若没有，但已有实质产品说明，则导入该说明，不另写一份唱反调的。若什么都没有，才根据仓库表层信息起草，同样要等确认。未确认的草稿不能拿来当「需求基线」或「这不合理」。

之后凡是要改业务代码、数据脚本、云资源，或把生成的说明/规范写成正式文件，都必须先给方案再等人说可以。默认只报告。

**Why this priority**: 对应宪章原则 II。自动落盘是幻觉污染仓库的入口，必须在第一条可用路径上就能演示。

**Independent Test**: 三种仓库（有规格驱动 / 仅有产品说明 / 什么都没有）各走一遍初始化，均在确认前停止；拒绝一份文档草稿后磁盘上无正式稿；未确认前后续命令不以草稿为对错标准。

**Acceptance Scenarios**:

1. **Given** 仓库已有规格驱动宪章或功能规格，**When** 用户初始化，**Then** 技能导入为草稿并等待确认，不另写冲突的产品说明，也不在确认前做全模块深潜。
2. **Given** 无规格驱动但已有实质产品说明，**When** 用户初始化，**Then** 导入该说明为草稿并等待确认。
3. **Given** 两者都没有，**When** 用户初始化，**Then** 起草产品说明草稿并等待确认；未确认前不当作验收标准。
4. **Given** 用户选择跳过说明或宪章，**When** 继续使用技能，**Then** 仍可做技术向扫描，但不得用未确认草稿判定「需求是否合理」。
5. **Given** 技能建议改业务文件或正式落盘文档，**When** 用户尚未确认，**Then** 磁盘上的业务文件与正式文档保持原样。

### User Story 3 - 查看状态、推进待办，贴报错就能分诊 (Priority: P1)

研发人员每天问「现在先做什么」。技能给一行健康摘要，并列出当前未关闭的待办（可按阻断/高优先级排序或过滤）。待办可以认领、可以关闭。条数**没有**「最多三条」上限：有多少未关闭的阻断与高优先级项，日常状态就应能看到多少。

出错时把终端报错直接贴进对话即可分诊：技能把它当正式证据，整理成问题与待办。密钥、口令、私钥、明显身份信息在落盘和回复里都必须去掉。分诊默认不改业务代码。

**Why this priority**: 没有状态与分诊，治理台只是档案柜。脱敏来自宪章安全约束。日常状态不再以三条为硬门禁。

**Independent Test**: 放入十条未关闭的阻断/高优先级待办后看日常状态，十条都能看到（不被截成三条）。再贴一段含伪密钥的堆栈：得到待办，秘密原文不可恢复，业务代码未被改。

**Acceptance Scenarios**:

1. **Given** 存在十条未关闭的阻断或高优先级待办，**When** 用户做日常状态查看，**Then** 这十条均可被看到，不得因「最多三条」被截断。
2. **Given** 待办优先级混杂，**When** 用户查看状态，**Then** 阻断与高优先级项默认排在前面或可被过滤突出；较低优先级可以默认折叠，但不得用三条上限代替过滤。
3. **Given** 用户认领或关闭一条待办，**When** 再次查看状态，**Then** 权威清单已更新。
4. **Given** 用户把堆栈贴进对话并分诊，**When** 处理结束，**Then** 产生问题与待办，粘贴本身即为证据（不必先存文件）。
5. **Given** 粘贴含秘密形态字符串，**When** 查看回复与治理台，**Then** 秘密已被替换；业务代码零自动写入。

### User Story 4 - 先看地图，再打开文件 (Priority: P2)

研发人员要弄清模块在哪。技能产出导航地图、带职责的目录概览，以及人能读的结构关系图，全部放进治理台。依赖目录、构建产物、日志和忽略清单不进扫描。已有地图时，只更新变更过的文件；单个文件读失败不能让整次失败。

此后在同一仓库里找东西或改东西，助手必须先读地图和说明索引。根目录无过滤递归翻找视为错误用法。用户若要求把图写进业务仓库，仍须先确认。

**Why this priority**: 对应宪章原则 III。降翻目录成本可以在治理台可用之后独立交付。

**Independent Test**: 含依赖目录的中小型仓库生成地图；依赖目录不在结果里。改几个业务文件后再更新，只处理变更。用同一句「某某能力在哪」对照：有地图时不出现对整棵树或依赖目录的无过滤遍历。

**Acceptance Scenarios**:

1. **Given** 仓库含依赖、构建产物或日志，**When** 用户请求梳理结构，**Then** 这些路径被跳过，地图与结构图写入治理台。
2. **Given** 地图已在且仅少量文件变更，**When** 再次梳理或增量更新，**Then** 只分析变更文件；单文件失败不导致整次失败。
3. **Given** 地图或说明索引已存在，**When** 用户请助手定位某能力，**Then** 助手先读地图/索引再打开目标文件。
4. **Given** 用户要求结构图落入业务目录，**When** 技能准备写入业务树，**Then** 先出示草案并等待确认。

### User Story 5 - 缺的说明可补，改动可评，踩过的坑能留下 (Priority: P2)

技能检查一组核心说明是否缺失（助手说明、产品说明、设计、接口、部署、排障）。缺了就问：用户自己补，或技能起草。草稿可改，只有确认后才写成正式文件。代码已变说明没跟上，只提示不一致，默认不自动改说明。

对本地改动做轻量评审：每条有效结论必须有推理和对应片段，空话不算数。用户可把条目标成确认问题、误报或稍后。确认过的真实问题进入规范库，后面再生成或再评审时要带上。阻断级必须打断；其余进报告。没有改动时要直说没有可评的，不许给空泛满分。

**Why this priority**: 文档双模式来自原则 II；有证据的变更评审与规范沉淀来自原则 IV。定期全量体检不在本版本。

**Independent Test**: 缺说明的仓库能列出缺失并走「起草 → 未确认不落盘 → 确认后落盘」。再对含故意缺陷的本地改动评审，每条能对上「为什么」和「哪一段」；确认一条后，同类问题再次出现时应引用已沉淀规范。

**Acceptance Scenarios**:

1. **Given** 缺少一项或多项核心说明，**When** 用户做文档治理或初始化，**Then** 列出缺失并提供自备 / 起草两种补齐。
2. **Given** 用户选择起草，**When** 草稿生成，**Then** 可编辑；未确认则正式位置不被覆盖。
3. **Given** 代码与产品/设计/接口说明不一致，**When** 做一致性检查，**Then** 只提示过期或不符，自动改写须再确认。
4. **Given** 存在本地变更，**When** 用户请求评审，**Then** 每条有效结论含推理与引用片段；无证据句子视为不合格输出。
5. **Given** 用户确认某条为真实问题，**When** 后续再评审同类改动，**Then** 规范库中的该约束被加载，而不是当作全新发现。
6. **Given** 用户标为误报，**When** 查看规范库，**Then** 该条不作为强制约束。
7. **Given** 没有本地变更，**When** 用户请求评审，**Then** 明确「没有可评的变更」，不输出空泛通过。

### User Story 6 - 做过什么能查、能按时间段交出去 (Priority: P3)

初始化、梳理、补文档、评审、分诊这些动作都要留下谁（或哪次会话）、何时、输入、输出；若该步有助手推理，推理一起留。与治理相关的对话在脱敏后可留下摘要；能判断本轮想改什么时记下目标和涉及文件，判断不了就标「未解析」，不许编。用户可按时间范围导出一份给别人复盘的记录。

**Why this priority**: 仍属原则 I 的审计要求，可在主循环可演示之后交付；不是下一版本的全量体检。

**Independent Test**: 连续做初始化、状态、分诊、评审后能看到对应操作记录；导出某一时间窗，第三人能看懂做过什么，且无未脱敏秘密。

**Acceptance Scenarios**:

1. **Given** 用户完成一次治理命令，**When** 查看审计，**Then** 能看到类型、时间、输入摘要、输出摘要；含推理则一并在。
2. **Given** 对话里表达了改动意图，**When** 技能解析本轮，**Then** 能记下主要目标与涉及文件，或标记未解析，禁止编造。
3. **Given** 用户指定时间范围导出，**When** 导出完成，**Then** 得到可复盘记录且秘密已脱敏。

---

### Edge Cases

- 治理台已存在时再次初始化：不覆盖用户已改过的治理文件，只补缺失骨架，确认流照走。
- 技能源码仓库与用户业务仓库不是同一个：禁止把用户业务写入技能仓库，也禁止把技能仓库的治理文件写进用户项目。
- 中文交互：待办、评审、报告用中文；命令名保持英文斜杠命令。
- 超大仓库达不到中小型时限：必须说明正在做全量或会更慢，禁止假装增量已完成。
- 下一版本才做的能力（定期全量体检、提交钩子、单测补全、高危徽标）不得作为本功能验收前置。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 技能必须在目标仓库建立独立治理台，保存导航地图、说明索引、评审、开发日志、规范库与待办；默认禁止写入业务源码树。
- **FR-002**: 治理台必须跨会话可用；元数据有效时禁止强制全量重扫。
- **FR-003**: 治理台必须仅本地（个人忽略），禁止写入仓库共享忽略规则。
- **FR-004**: 元数据损坏或项目文件变更时，必须修复或增量更新；禁止静默丢数据，禁止无提示全量覆盖已确认内容。
- **FR-005**: 每次扫描、说明生成、评审、分诊与相关对话必须留下审计（会话或操作者、时间、输入、输出；有推理则含推理），并支持按时间范围导出。
- **FR-006**: 存在规格驱动宪章或功能规格时必须导入为草稿并等待确认，禁止另写冲突产品说明，确认前禁止以其为基线。
- **FR-007**: 无规格驱动时必须导入或起草产品说明为草稿并等待确认 / 修订 / 跳过；未确认禁止当作验收标准。
- **FR-008**: 写入业务代码、数据脚本、云资源，或将生成说明/规范正式落盘前，必须先给方案并获得明确确认；默认只报告。
- **FR-009**: 核心说明缺失时必须列出清单，并提供用户自备与起草确认两种补齐；未确认不得覆盖正式说明。
- **FR-010**: 必须能提示产品/设计/接口说明与代码不一致；默认只提示。
- **FR-011**: 日常状态必须给出健康摘要与未关闭待办；阻断与高优先级项不得因条数上限被截断。禁止把「最多三条」作为硬门禁。较低优先级可以默认折叠或排后。
- **FR-012**: 对话粘贴必须可作为分诊证据，不必先存文件。
- **FR-013**: 证据、对话摘录与导出落盘前必须脱敏（密钥、口令、私钥、明显个人身份信息）。
- **FR-014**: 必须能生成导航地图与人能读的结构关系图及带职责的目录概览，写入治理台。
- **FR-015**: 扫描必须跳过依赖目录、构建产物、日志及配置的忽略路径；必须支持仅变更文件的增量；单文件失败不得中断整批。
- **FR-016**: 地图或说明索引存在时，后续协作必须先读它们；无过滤全库递归不得作为默认找文件方式。
- **FR-017**: 必须能对本地变更做评审；有效结论必须含推理与引用片段；无证据结论为不合格输出；无变更时必须明示无可评内容。
- **FR-018**: 用户必须能将评审条目标为确认问题、误报或待处理；确认问题必须进入规范库并在后续生成与评审中加载。
- **FR-019**: 阻断级必须打断展示；非阻断进入报告，不得用无证据的空泛长评语代替评审。
- **FR-020**: 必须能在脱敏后保留治理相关对话摘要，并在可判断时记录本轮意图；不可判断时标未解析，禁止编造。
- **FR-021**: 用户以中文交互时，待办、评审与报告正文必须中文；命令名与路径保持英文。
- **FR-022**: 本版本不得把定期全量体检、提交钩子强制、单测助手、高危徽标当作交付前置。

### Key Entities

- **治理台**：仓库旁的独立资料区，跨会话保存本技能的全部治理资产。
- **基线草稿**：导入或起草的宪章/规格/产品说明，仅确认后成为判定依据。
- **导航地图**：给人与助手用的结构契约（模块、关键文件、能力、常改位置）。
- **说明索引**：核心说明是否存在、是否可能过期。
- **待办**：可认领可关闭的行动项，带优先级。
- **评审条目**：一次变更上的发现，含推理、片段与用户处置。
- **规范条目**：由确认问题沉淀的约束，供后续加载。
- **审计记录**：一次操作或一轮相关对话的留痕，可按时间导出。
- **证据**：分诊或扫描用的输入摘录，落盘前已脱敏。

### Governance Constraints *(mandatory if the feature writes files, reviews code, stores session data, or changes daily UX)*

对照 `.specify/memory/constitution.md`。不适用的条目可删除；适用的条目禁止静默忽略。

- **GC-001**: 持久化必须使用 `.pm/`（或已文档化的元数据目录），禁止污染业务源码。
- **GC-002**: 修改应用代码、SQL 或云资源必须经用户明确确认。未确认的 PRD/宪章禁止当作验收标准。
- **GC-003**: 密钥与对话内容在持久化或导出前必须脱敏。
- **GC-004**: 评审或质量输出必须包含推理链与引用代码片段；无证据结论不合规。
- **GC-005**: 日常状态不得以「最多三条」截断未关闭的阻断或高优先级待办。对话粘贴必须可作为分诊证据。
- **GC-006**: 当地图/文档索引存在时，Agent 读文件必须优先它们，禁止默认全库递归。
- **GC-007**: 本规格及派生的 plan/tasks/用户可见报告正文必须中文优先。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 未治理仓库首次初始化后，用户在 5 分钟内能确认：治理台已在、业务文件未被改写、下一步是确认说明/宪章或查看今日待办。
- **SC-002**: 新开对话后，用户不必等待一次全库重扫就能看到上次待办或地图。中小型仓库上，有地图时的更新体感在数秒内；全量梳理等待不超过约 30 秒。
- **SC-003**: 存在 10 条未关闭的阻断或高优先级待办时，日常状态能看到这 10 条，而不是只露出前 3 条。用户可以认领与关闭待办。
- **SC-004**: 含伪秘密的粘贴分诊后，回复与落盘都无法找回原文秘密；业务代码零自动修改。
- **SC-005**: 同一句定位提示下，有地图时助手不会去无过滤翻整棵源码树或依赖目录。
- **SC-006**: 说明起草在未确认前不覆盖正式文件；确认后用户能在约定位置看到终稿。
- **SC-007**: 对故意带缺陷的变更，评审人能在约 15 秒内从每条有效结论对上「为什么」和「哪一段」；无证据套话视为失败。
- **SC-008**: 用户确认一条问题后，后续同类评审会提到已沉淀约束，而不是全新发现。
- **SC-009**: 用户能导出某时间段治理记录，第三人可复盘做过什么，且无未脱敏秘密。
- **SC-010**: 中文用户看到的待办、评审与报告为中文；命令名仍为英文斜杠命令。

## Assumptions

- 「开发 skill」指安装到编码助手中的 PM Manager 治理技能，以及它在目标仓库操作的本地治理台；不是新做云端项目管理，也不替代规格驱动交付链。
- 斜杠命令沿用现有英文名称（初始化、状态、下一条、完成、分诊、全量、结构、导出、宪章等），本规格约束行为，不要求改名。
- 当前宪章正文为四条核心原则（I–IV）。日常状态**不以 Top3 为门禁**；粘贴分诊与脱敏仍为必做。
- V1.0 / V1.1 边界以宪章冻结段落为准。
- 性能数字针对中小型仓库；更大仓库必须明示会更慢。
- 默认为单人本地使用；本版本不解决多人实时同步同一治理台。
- 创建治理台骨架的安装步骤可以已存在；本规格要求技能在其上落实确认流、地图优先、评审证据与脱敏。
- 规格驱动工具与本技能可共存于同一仓库；禁止静默覆盖对方产物。
